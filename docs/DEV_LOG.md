# 과제 2 개발 기록

## 2026-10-28 — 사진 인식 API 설정 원인 확인

- **발견한 문제 또는 개선 필요성:** 사진 등록 화면에 API 키가 없다는 안내가 표시되었습니다. 프로젝트 루트의 `.env`와 프로세스 환경 설정을 확인한 결과 `.env` 파일은 있었지만 `OPENAI_API_KEY` 값이 비어 있었습니다. 따라서 현재 오류는 파서가 키를 못 읽는 문제보다 실제 키가 아직 설정되지 않은 상태 때문입니다.
- **내가 AI에게 요청한 내용:** `.env` 로딩과 오류 원인을 확인하고, 실제 키를 노출하지 않으면서 키 없음·인증 실패·잔액/사용 한도·요청 제한을 구분해 달라고 요청했습니다.
- **적용한 해결 방법:** `.env` 파서가 빈 프로세스 환경값 대신 비어 있지 않은 로컬 `.env` 값을 읽도록 확인·보강했습니다. 사진 API 오류를 상태 코드와 API 오류 코드로 구분하고, 서버 로그에는 키의 설정 여부만 표시하도록 유지했습니다. 기본 모델은 이미지 입력과 Structured Outputs를 지원하는 `gpt-4o-mini`입니다. 기존 localStorage 인벤토리와 수동 등록 경로는 API 키와 독립적으로 유지했습니다.
- **테스트 결과:** 임시 파일에서 비밀이 아닌 테스트 문자열과 모델 설정을 로드하는 테스트가 통과했습니다. 키 미설정 HTTP 응답과 인증/결제·사용 한도/요청 제한 오류 분류 테스트가 통과했습니다. 현재 실제 `.env`의 키는 비어 있어 실제 OpenAI 요청은 수행하지 않았습니다.
- **남은 한계:** 사용자가 로컬 `.env`에 키를 직접 추가하고 서버를 재시작해야 합니다. API 키는 채팅으로 보내지 않아도 됩니다.

## 2026-10-28 — 제품 사진·영수증 인식 결과 보강

- **발견한 문제 또는 개선 필요성:** 사진 인식 결과에 제품 바코드, 제조일, 영수증 구매일 정보가 구조화되어 있지 않았고, 제품 데이터 조회와 출처 표시가 연결되어 있지 않았습니다.
- **내가 AI에게 요청한 내용:** 상품명/브랜드/종류/수량/바코드/보관 정보/라벨 소비기한/제조일을 뽑고 사용자가 확인·수정한 뒤 일괄 등록하도록 요청했습니다.
- **적용한 해결 방법:** Responses API에 strict Structured Outputs 스키마를 적용하고, 포장에 명시된 소비기한과 제조일, 영수증에 인쇄된 구매일을 서로 분리했습니다. Open Food Facts에서 바코드를 먼저 조회하고, 바코드가 없으면 제품명 및 브랜드의 완전 일치가 확인된 결과만 사용합니다. 불일치·모호한 검색 결과는 적용하지 않습니다. 확인된 결과에는 출처 URL과 조회 시각을 저장하고, 24시간 캐시 및 요청 제한을 둡니다. 인벤토리는 제품 사진, 일치된 제품 사진, 내장 SVG 순서로 이미지를 선택하고 깨진 이미지에는 기존 fallback을 사용합니다.
- **테스트 결과:** Responses 이미지 입력과 JSON Schema 요청 구조, 정확 바코드 일치/캐시/출처 데이터, 유사 상품 오매칭 거부 테스트가 통과했습니다. 공개 Open Food Facts 바코드 조회를 실제 네트워크로 실행해 정확 매칭, 출처, 조회일, 이미지 URL을 확인했습니다.
- **남은 한계:** 제품 DB는 협업 데이터이며 모든 상품이 등록되어 있지 않습니다. 제조사 공식 DB와 식품안전나라 제품별 정보의 범용 연동은 구현하지 않았고, 정확한 외부 매칭이 없는 경우 정보는 비워 둡니다. 실제 사용자 영수증/제품 사진을 이용한 OpenAI 인식은 키 미설정으로 검증하지 못했습니다.

## 2026-10-28 — 확인일 추천과 소비기한 분리

- **발견한 문제 또는 개선 필요성:** 제품 날짜를 등록일이나 구매일로부터 임의 계산하면 소비기한처럼 오해될 수 있으므로 실제 날짜와 재고 확인일을 더 엄격히 분리할 필요가 있었습니다.
- **내가 AI에게 요청한 내용:** 포장에 확인된 실제 소비기한, 제조일 기반 계산(정확한 제품 기준이 있을 때만), 출처가 있는 추천 재고 확인일, 날짜 미확인을 구별해 달라고 요청했습니다.
- **적용한 해결 방법:** 제조일/구매일을 실제 소비기한으로 변환하지 않습니다. 현재는 영수증에서 구매일이 확인되고 보관 장소가 냉장인 생 가금류 또는 다진 소고기 등 제한된 분류에 대해서만 FoodSafety.gov의 냉장 보관표를 출처로 재고 확인일 초안을 제시하며, 사용자가 검토·선택해야 저장합니다. 이 날짜는 실제 소비기한으로 표기하지 않습니다. 다른 식품은 출처 있는 제품별 기간이 확인되지 않으면 날짜를 비워 둡니다. 포장 개봉 안내는 포장에 읽힌 경우만 별도 근거와 함께 표시합니다.
- **테스트 결과:** 생 닭고기+냉장+구매일 조건의 날짜 제안과 출처, 일반 우유/냉동 보관/잘못된 날짜에서는 제안하지 않는 테스트가 통과했습니다. 전체 자동 테스트 14개가 통과했습니다.
- **남은 한계:** 제조일과 정확한 제조사의 제품별 보존 기간을 함께 검증할 제품 DB가 없어 제조일 기반 계산 기능은 의도적으로 적용하지 않았습니다. 안전한 보관은 항상 제품 라벨 및 관할 식품 안전 안내를 우선해야 합니다.

## 2026-10-28 — 제품 시각 식별과 인터넷 제품정보 검색

- **기존 사진 인식 기능의 한계:** 기존 요청은 포장 글자를 읽고 항목을 나열하는 데 초점을 두었습니다. 제로/일반 맛, 용량, 포장 모양을 비교하는 식별 필드와 검색 출처 기반 제품정보 단계가 없었습니다. 프로젝트의 `.env`에는 OpenAI 키 값이 비어 있어 실시간 API 검색도 호출할 수 없는 상태입니다.
- **내가 AI에게 요청한 내용 / AI 활용 과정:** 포장 글자뿐 아니라 로고·색상·패키지 모양·상품 이미지 같은 시각 특징을 함께 비교하고, 맛과 용량이 다른 상품은 구분하며, 모호한 경우 후보를 사용자가 선택하게 요청했습니다. 사진 인식 Structured Outputs에 variant, 용량, 시각적 근거, 후보명을 추가했습니다. 제품 조회는 바코드/정확 이름 Open Food Facts 검색 후 검색용 모델의 Responses API `web_search`를 별도로 사용하도록 구성했습니다.
- **제품 검색 API 추가:** 초기에는 `gpt-4.1-mini`에 `web_search.filters`를 함께 전달했으나 실제 호출이 “filters not supported” 400으로 실패했습니다. 도메인 필터 검증을 제거하지 않고 web search와 필터를 지원하는 `gpt-6-luna`를 기본 검색 모델로 변경했습니다. 공식 제조사, 식약처/식품안전나라, Open Food Facts, 지정 판매처 도메인으로 검색을 제한하고 실제 검색 결과에 포함된 출처 URL만 반환합니다. 바코드, 브랜드, 상품명, 용량, 버전을 확인하고 출처 인덱스가 확인된 사실만 자동 입력합니다. 영양은 표시 기준량과 함께 저장하고, 미개봉/개봉 후 보관방법을 별도 필드로 기록합니다. 제조일 기준 소비기한 기간은 제조사 출처로 확인된 경우만 제조일에서 제안하고 사용자가 확인해야 저장됩니다. 일반 식품 소비기한을 구매일로부터 추정하지 않습니다.
- **매칭 오류와 수정:** 처음의 정확 이름 비교만으로는 `얼박사 제로`와 일반 얼박사, 신라면과 신라면 골드, 210g/다른 용량을 충분히 구분할 수 없었습니다. 상품명·버전·브랜드·용량을 전부 대조하고, 크기 정보가 모순되면 검색 결과를 자동 적용하지 않도록 바꿨습니다. 바코드와 OCR 용량이 다르면 충돌 후보를 보여주고, 검색을 다시 수행할 때 그 바코드를 버려 사용자가 고른 이름을 다시 조회합니다. 브랜드/용량 정보가 없는 ‘일반 냉장 우유’는 특정 브랜드 영양값을 대입하지 않습니다.

  - 스팸 클래식: CJ더마켓 공식 제품 페이지에서 200g, 미개봉 상온 보관을 확인했습니다. CJ 공식 FAQ는 남은 스팸을 밀폐용기에 담아 냉장하고 빠른 시일 내 먹도록 안내합니다. 출처: https://m.cjthemarket.com/the/product/product-main?prdCd=40134660 및 https://m.cj.co.kr/kr/support/faq/1087

- **내가 AI에게 요청한 내용:** 카메라·바코드 이미지·직접 입력을 지원하는 EAN/UPC 등록을 기존 API에 연결하고, 일치 제품의 이름·브랜드·용량·사진·영양을 미리 채우며, 바코드/사진 등록 상품에 기준량을 구분한 영양 상세와 안전한 총 열량 계산을 추가하도록 요청했습니다.
- **적용한 해결 방법:** 브라우저 `BarcodeDetector`가 지원하는 경우 후면 카메라와 이미지에서 EAN-8/EAN-13/UPC-A/UPC-E/ITF-14 등을 읽고, 미지원 환경에는 직접 숫자 입력을 제공합니다. `/api/lookup`의 정확한 바코드 결과만 사용하며 결과가 없으면 해당 숫자를 보존해 수동 등록으로 이어집니다. 기존 localStorage 정규화 구조에 있던 브랜드·용량·이미지·영양·출처 필드를 재사용했습니다. 영양 상세는 카드에서 펼쳐 보는 형태로 추가하고, 포장 단위와 기준 단위(예: 200g 대 100g)가 일치할 때만 포장 및 현재 재고 열량을 계산합니다. 다중 포장 표기, 단위 불일치, 영양값 미확인에서는 계산을 생략합니다.
- **실제 테스트 결과:** 테스트 19개 통과, `node --check app.js`, `lib/inventory-data.js`, `server.js` 통과. 실제 Open Food Facts 바코드 `3017620422003` 조회는 Nutella, Ferrero, 400g, 상품 이미지, 539kcal/100g 및 탄수화물·당류·단백질·지방·나트륨을 반환했습니다. 로컬 서버 `/`와 `/api/lookup` 종단 간 응답에서 상품 매칭 및 영양 기준량을 확인했습니다. 제품 포장 200g, 100g당 100kcal, 수량 3개는 포장 200kcal/보유량 600kcal로 계산하고, g/mL 불일치와 6×다중포장은 계산하지 않는 단위 테스트를 추가했습니다.
- **발생한 문제와 대응:** 처음 3003에서 서버를 시작하자 이미 구버전 프로젝트 프로세스가 포트를 사용해 `EADDRINUSE`가 발생했습니다. 별도 3004 포트에서 신규 코드를 검증한 뒤, 해당 프로세스가 이 프로젝트 폴더에서 실행된 로컬 개발 서버임을 확인하고 재시작했습니다. 재시작 뒤 3003의 `/api/lookup`가 영양정보를 포함해 반환하는 것을 다시 확인했습니다. Vercel 설정/배포에는 변경을 가하지 않았습니다.
- **남은 한계:** 실제 카메라 권한과 바코드 사진을 가진 기기에서 스캔하는 테스트는 하지 못했습니다. `BarcodeDetector` 지원은 브라우저/OS에 따라 다르고 HTTPS 또는 localhost가 필요합니다. 지원하지 않는 경우 숫자 직접 입력은 유지됩니다. Open Food Facts는 사용자 기여 DB이므로 포장 라벨과 대조해야 하며 제품 또는 영양정보가 없을 수 있습니다. DB가 제공하는 칼로리만 표시하고 불확인 값은 미확인으로 남깁니다. Vercel 배포 설정은 변경하지 않았으며, 프로젝트에 Git 저장소/원격이 없어 배포는 수행하지 않았습니다.

## 2026-10-28 — 최종 제출용 History/Favorites 및 배포 점검

- **문제 상황:** 기존 등록 흐름은 정상 작동했지만 같은 제품을 다시 찾거나 즐겨찾는 식품을 빠르게 추가할 기록 UI가 없었습니다. Vercel은 공개 API의 공유형 인증이 없어 AI를 무조건 활성화하면 비용 위험이 남았습니다.
- **AI에게 요청한 내용:** 최근 등록 식품과 즐겨찾기를 localStorage에 저장하고 한 번의 버튼으로 새 등록을 시작하되, 과거 구매일과 소비기한은 복사하지 않도록 요청했습니다. Vercel AI 활성화 조건도 함께 확인했습니다.
- **적용한 해결 방법:** `my-fresh-bag-history-v1`, `my-fresh-bag-favorites-v1`를 기존 인벤토리 키와 분리했습니다. 식품 등록 시 최근 기록을 저장하고 카드의 별 버튼으로 즐겨찾기를 유지합니다. 최근/즐겨찾기 항목은 이름·브랜드·용량·이미지를 보여주며 `다시 등록`은 수량 1과 빈 날짜로 수동 등록 화면을 엽니다. 기록 삭제와 즐겨찾기 해제를 추가했습니다.
